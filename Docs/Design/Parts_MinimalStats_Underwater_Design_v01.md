# VoxelOn_2nd — 파츠 간소화 및 수중 시각 효과 설계서 v0.1

- 설계 주체: PD × Max
- 날짜: 2026-11-13
- 문서 상태: 설계 기준 합의 / 개발 구현 및 QA 미검증
- 범위: 기존 무기 9개 기본 수치 간소화안과 구별되는 **파츠 기본 수치** 및 **수중 화면 색감** 문제.
- 목적: 지나치게 복잡한 수치 UI를 단순하게 만들고, 확정 사양을 GitHub에서 반복 개정하는 개발 체계를 구축한다.

## 1. 기본 설계 원칙
1. 게임에서 체감되는 필수 기본 수치만 사용자에게 노출한다. 엔진 내부에 필요한 물리·애니메이션 상수는 지우지 않고 내부 규칙으로 관리한다.
2. `기본 수치`, `고유 동작`, `특수 기능/아이콘`, `장착 제약`을 분리한다.
3. `특수 기능`은 반드시 하나의 파츠 종류에만 묶지 않는다. 예: 머리나 몸통에도 부스터 강화 옵션 가능.
4. 버전별 사양 변경은 문서 커밋부터 시작하고, 개발자가 구버전 호환 영향을 검토한 다음 게임에 적용한다.

## 2. 간소화 파츠 기본 수치

| 파츠 종류 | 노출할 수치 | 설계 의도 |
|---|---|---|
| 머리 | 감지 성능, 무게 | 락온/레이더 거리 대표값 단순화. 필요하면 내부적으로 각 거리 산출 |
| 몸통 | 내구도, 에너지 용량, 무게 | **피해 감소율 삭제 확정**. 생존력은 내구도, 실드는 별도 기능 |
| 다리 | 이동력, 점프력, 무게 | 방향별 속도, 중력, 턱 넘기 등은 이동 방식별 내부 규칙 |
| 백팩 | 부스터 성능, 무게 | 부스터가 없는 백팩 허용. 에너지 소모/수직 추력 등은 내부 규칙 |
| 좌우 팔 | 별도 수치 삭제 검토 | WISP는 짧은 상박이 몸통에 속하고 하박은 무기 교체식. 기존 팔 조작·안정성은 검증 후 처리 |

### 파츠 고유 조건 및 특수 기능
- 머리: 락온 향상, 락온 안정화, 조준 보정 강화 등은 기본 감지 수치와 별개 특수 기능.
- 몸통: 실드 지원 유무는 별도 특수 기능. '하박 가드 자세'와 별개.
- 다리: 이족·전차형·사족·호버형 등 이동 종류와 점프/체공/고속 이동 지원 여부는 **기능과 이동 타입**으로 분리.
- 백팩: 서브 무기 슬롯 0/1/2개, 부스터 유무, 기능 유형. 공격·요격·교란 드론은 **서브 무기 아닌 백팩 고유 기능**이며 해당 백팩의 서브 무기 슬롯은 0개.
- 무게는 `plannedWeight` 보관값으로 존재하며 게임 적용 여부는 별도 구현 필요. 구현 없이 작동한다고 간주하지 않는다.

## 3. 수중 화면 색감 문제 (버그 후보)
### 관찰
PD: 바다속으로 진입해도 화면이 살짝 파랗게 변하는 연출이 보이지 않음. 개발자는 실제 수중 판정·카메라 위치·렌더 파이프라인 상태를 확인하여 **효과 누락/미구현/수중 판정 실패 중 원인을 구분**한다.

### 최소 요구
- 카메라가 수면 아래에 있을 때 **은은한 청색 계열 톤**이 적용되어야 한다.
- 거리감 있는 수중 안개/가시거리 감소는 과하지 않게 적용.
- 수면 경계 통과 시 갑작스러운 화면 깜빡임 없이 자연스럽게 전환.
- 수면 밖에서는 기존 색상과 시야가 회복되어야 한다.
- HUD 및 조준점은 필터 때문에 읽기 어려워지지 않아야 한다.
- 부가 기포/음향 연출은 이번 최소 수정 범위 밖.

### 검수 시나리오
1. 수면 위 스크린샷.
2. 수면 직하 스크린샷: 명확하지만 과하지 않은 청색 톤 확인.
3. 깊은 수중 스크린샷: 색조와 안개 확인.
4. 수면을 반복 횡단하여 전환, HUD 가독성, 성능 문제 확인.
5. 작업 전후 동일 카메라 위치 비교 및 짧은 결과 보고.

## 4. 기존 구현과 호환성 필수
- 현재 `Docs/Balance/PD-Balance-Template.json`의 WISP/BASTION/TARANTULA는 머리 5, 몸통 4, 각 팔 3, 다리 11, 부스터 4개 항목을 가진다.
- 기존 속성(`armor`, `lockRange`, `radarRange`, `boostDrain` 등)을 기획서가 바뀌었다는 이유만으로 바로 삭제하거나 이름 변경하지 않는다.
- `armor`는 신규 밸런스 기획에서 **제외**. 실제 피해 계산에서 무효화하거나 마이그레이션할 방법은 영향 검토·테스트 후 적용한다.
- 감지 성능/부스터 성능 같은 대표값의 실제 내부 계산식은 코드 확인 후 개발자가 최소 설계를 제안한다.
- 기존 조작, 저장 파일, 빌드, 3개 기체 이동 유형이 깨지지 않아야 한다.

## 5. 반복 업데이트 운영 방식
1. **PD 결정:** 변경할 값·기능·우선순위를 대화에서 승인.
2. **Max 기획 반영:** 버전 문서와 변경 이력 작성 후 `main`에 기획 문서만 커밋.
3. **길이 기술 검토:** 최신 설계 문서 읽기, 기존 Unity 코드/JSON과 차이점·충돌·예상 영향 보고.
4. **길이 구현:** 명시적으로 승인된 작업만 `work`에서 수정, 기존 원본 보존, 필요한 테스트·Unity 빌드.
5. **검증:** 실제 게임 화면/입력/동작과 전후 스크린샷을 PD와 Max가 검수.
6. **개선 반복:** 미흡한 부분은 다음 버전에서 바꾸고 검증 결과를 이력에 누적.

### 상태 체계
`draft → approved → implementation → verified`. 문서 커밋이 곧 자동 실행 승인은 아니다. 기존 작업 큐의 `ready` 규칙을 우회하지 않는다.
