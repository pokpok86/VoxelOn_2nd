# 시스템 확장 30분 단위 작업 — 1차 데이터 저장 구조

작성: 2026-11-06. 범위는 기존 밸런스 파일을 보존하면서 저장 가능한 기체 설계 8칸을 위한 데이터 형식 기반을 추가하는 것이다. Unity 빌드/실행 검증까지 완료했다. `main`은 변경하지 않았고 아직 커밋·푸시하지 않았다.

## 변경

- `BalanceDocument` 저장 형식을 v1에서 v2로 올렸다.
- 고정 ID `DESIGN_01`~`DESIGN_08`을 추가했다. 각 항목에는 이름, 기체 ID, 독립된 4개 장착 슬롯이 저장된다.
- v1 파일을 읽으면 기존 세 기체의 무장을 처음 세 슬롯에 그대로 옮기고, 나머지 다섯 슬롯은 WISP 기본값으로 채워 v2 문서로 메모리 변환한다.
- 읽기만 했을 때 원본 파일은 쓰지 않는다. 사용자가 저장할 때만 v2로 저장하고 이전 바이트를 `.bak`으로 보존한다.
- 중복/미등록 설계 ID, 기체 ID, 장착 부적합을 거부한다. 미래 형식 버전 거부와 수치 범위 검사는 유지했다.
- 플레이어의 사용자 밸런스 파일은 테스트에서 읽거나 덮지 않았다. 테스트 파일은 `Logs/Balance-Editor-Test-*` 분리 폴더에 생성했다.

## 검증 근거

- Unity 6000.6.7f1 Windows 빌드 성공: `VOXSKY_BUILD_PASS 237233850 bytes`, `Logs/BalanceSchema-V2-Iteration1-Build-Final.log`.
- 실제 빌드된 플레이어의 밸런스 편집/저장 검사: `BALANCE_EDITOR_STUDY_PASS 46 checks; 10 images`, `Logs/BalanceSchema-V2-Iteration1-EditorStudy-Final.log`.
- 실제 빌드된 플레이어 기본 회귀: `VOXSKY_SMOKE_PASS 358 checks`, `Logs/BalanceSchema-V2-Iteration1-Smoke.log`.
- 검증 캡처는 `Docs/Screenshots/Balance-Editor-20261106/SchemaV2-Iteration1/`에 보관했다. 실제 저장/불러오기 화면에서 기존 파일 관리 화면은 확인되지만, 신규 8개 설계 슬롯 UI는 아직 표시하지 않는다.
- 첫 검사에서 백업 테스트가 실패했다. 저장 동작이 아닌 테스트가 `BalanceFiles.Load`로 v1 백업을 다시 v2로 변환한 값을 검사하고 있었다. 검사를 원본 백업 JSON 바이트의 버전 확인으로 바로잡은 뒤 전체 46개 통과했다. 제품 검증 기준은 낮추지 않았다.
- Unity가 빌드 시 자동 생성한 `Assets/Scenes/Arena.unity`와 구버전 갤러리 캡처 변경은 이번 작업에서 의도하지 않은 산출물이어서 저장소 기준으로 복원했다. 새로운 캡처만 새 폴더에 분리했다.

## 현재 한계와 다음 30분 단위

8칸은 데이터 객체와 검증만 추가된 기반이다. 현재 행거 화면은 여전히 세 기체의 기존 편집 흐름을 사용하며, 8칸 생성/복사/이름 변경/삭제/초기화 UI나 선택한 설계를 출격에 적용하는 연결은 없다. 또한 무기·파츠 배열은 아직 정적 기본 목록 길이와 ID에 묶여 있어 새 ID를 추가하려면 코드/아트 등록이 필요하다. 전투 엔진에서 새 무기·파츠 정의를 읽는 확장 레지스트리도 아직 미구현이다.

다음 순서는 8개 설계 슬롯을 편집 화면에 연결하고 각 슬롯을 재시작 후에도 불러오는 UI 검증이다. 그다음 안정 ID 기반 무기/파츠 정의 레지스트리를 만들고 새 무기 1종과 파츠 1종의 값이 실제 탄/기체 동작에 반영되는 수직 단계를 수행한다. 게임 규칙, 스킬, 중력 장치 또는 팀전은 이 단계에 섞지 않는다.
